Loop engineering

How a ticket becomes merged code without you driving each turn — and why the expensive model is deliberately kept out of the part that repeats.

This page assumes you have never run a loop. It explains the idea, the one property that makes it trustworthy, and the exact commands. The reference material lives in LOOP.md; this is the explanation.

1. The problem it solves

Ask an agent to do something and it will tell you it is done. Sometimes it is. The difficulty is that "I have completed the task" costs the model nothing to say and reads identically whether it is true or not. So you check. Then you ask for a fix. Then you check again. You are the loop, and you are the slowest part of it.

The fix is not a better prompt. It is to stop asking. Replace the question "are you done?" with a command whose exit code answers it, and put that command somewhere the agent cannot reach.

The one load-bearing idea

The agent never says whether it succeeded. It is not asked. A script outside the session runs the repository's own test suite and reads $?. That single change is the entire difference between a loop and a prompt you sent hopefully.

2. Four roles, and only two of them are models

The word "judge" hides an important split. Something has to decide what you want — that takes real intelligence. Something has to decide whether you got it — and that must not be a model at all, because a model can be argued into a yes.

RoleWhoRunsDecides
Architect Opus once, up front what "done" means — writes it as a failing test
Worker Luna once per iteration how to make that test pass
Gate no model every 5 seconds whether it passed — exit code and checksums
Referee Opus once, at the end whether the pass is the one you wanted

Why this is cheap

The Gate sits between the Worker and the Referee, and Opus never sees a red run. It is not in the polling loop, it does not read failure output, and it is not woken up between iterations. It thinks twice per ticket: once to decide what to build, once to check what came back.

ActorInvocations per ticketScales with iterations?
Opus2 — Architect, Refereeno
Lunaup to MAX_ITER, typically 1–4yes
Gateup to 72 per iterationyes — and free

The models are pinned in frontmatter, not chosen at runtime. .github/agents/loop-worker.agent.md declares model: ["GPT-5.6 Luna", "Claude Sonnet 5"], and the driver dispatches with code chat -m loop-worker. Change the model by editing that one line.

That the pin is honoured was proven on 2026-09-23. Two probe agents identical except for the model: line were dispatched back to back; VS Code's own session record — not the model's self-report — came back copilot/gpt-6-astra and copilot/gemini-3.8-flash. Had both said the same thing, the pin would have been decorative and every cost claim on this page worthless.

3. The cycle

0–2Opus, in your chatintake · spec · arm
3Luna + Gate, headlessgrind until green
4Opus, in your chatreferee the diff
5Opus, in your chatPR · close ticket
#PhaseWhat happensYou do
0Intake Reads the ticket and drafts the assertions, then asks you once about anything Jira left ambiguous confirm or correct
1Architect Writes those assertions as a real test, runs it, confirms it is red, commits it nothing
2Arm Copies scripts/loop.sh to tmp/ and fills it in nothing
3Grind Dispatch Luna → poll → verdict → repeat, until terminal or out of budget run one command, then watch
4Referee Opus reads the diff and accepts, re-arms, or abandons agree or push back
5Close Commit, PR with the Jira link, resolve the ticket approve the PR

You write requirements. It writes the spec.

This is the part that sounds harder than it is. Nowhere in the cycle are you asked to write a test. You give it the ticket — ordinary prose, the same words you would type into Jira — and phase 1 does the translation:

What you writeWhat it writes
“flag real differences, ignore noise” a test feeding it fixture page pairs and checking the verdict it emits
“it should be fast” a number — the suite must finish in under five minutes
“don’t hardcode selectors” a test that fails if any data-testid is declared outside pom.ts

That translation is the reason phase 0–1 runs on the expensive model. It is also the only place your judgement is really needed: phase 0 shows you the draft assertions before any code is written, with a proposed default next to every open question, so settling it costs you a sentence. Everything after that is mechanical.

4. Running one

Open Chat in the bot workspace, pick loop-architect in the mode picker, and type what you need. A ticket key, or a sentence — both work: 

WS-6673
the fragments package has no storybook coverage and it should

That agent is the entry point. It runs phases 0–2, hands you the grind, and is still there when you come back for phases 4–5. /loop <the same thing> also works from any agent — it is a shim that reads the same file — but the agent is the better route:

loop-architect agent/loop prompt
Modelpinned by the agentwhatever the picker happens to say
Lifetimethe whole job, referee pass includedone message
Where the rules live.github/agents/loop-architect.agent.mdreads that same file

Phase 2 ends by handing you this. Run it in a second terminal:

npm run cc -- serve          # watch at http://127.0.0.1:4747/loops
bash tmp/WS-1234-loop.sh     # the grind — minutes, not seconds

Why the start is a chat session and not a dashboard button

Phase 1 needs a model, and this system has a hard invariant that it never invokes one on its own — a "Run loop" button would be a path from a scheduled job to an agent editing another repository unattended. So a loop is always started by a person, in a chat session they are looking at. The dashboard's job is to let you watch, which is the part that was actually missing.

5. Cheating, and the four ways it is caught

Exit code 0 is necessary but not sufficient. There are four cheap ways to make a test suite pass without doing the work, and a worker under time pressure will find them. Each gets its own terminal state, and every one is a fail — not a warning.

StateThe cheatHow it is caught
tamperededit the test until it matches the code sha-256 over the spec, re-read on every poll
shrunkdelete the failing tests total count must exceed the baseline
suppressedeslint-disable instead of a fix occurrences counted before and after
cfg-tamperedraise the guard limit you are failing sha-256 over the config file

Two design details worth keeping. Integrity is checked before the exit code, so a run that edited the spec is tampered even if the suite is green and the test count went up. And the checks are cheap enough to re-run continuously, so an invalid run is caught in seconds instead of after it has spent its whole budget.

6. Most tickets are not loopable

This is the part that saves you the most time, and it is the part everyone skips. A ticket qualifies as a loop only if all four of these hold. Check them before you write a spec, not after you have burned a budget finding out.

TestIt fails when…Example that fails
The verifier is local "done" is decided by a remote system "prove the Jenkins stage ran" — the answer is on a build server, not in $?
The verifier is red today the named gate already passes yarn lint && yarn test is green on main, so it can never signal completion
The deliverable is machine-checkable the output is prose a design document — no exit code can judge an argument
The inputs exist the agent would have to invent data a merchant cohort list nobody has supplied yet — it will make one up

The most common mistake, by a distance

Naming the repository's existing suite as the gate. yarn test passing does not mean your ticket is done — it means your ticket is not represented in it. A loop needs a new assertion that fails right now.

cc loop start refuses to open a run whose verifier already exits 0. When you see that refusal, the design is working. Go write the failing test.

The subtle case: when the deliverable is tests

If the ticket is "write a Playwright smoke suite", the worker is writing the very thing a spec would normally be — so there is nothing to lock. Lock a meta-spec instead: a test asserting the suite exists, covers the four merchant types, finishes inside its time budget, and hardcodes no selectors. That is the file the worker may not touch.

A ticket that fails this triage is not a worse ticket. It is work for a normal chat session with a human reading the output — which is most work, and that is fine.

7. Reading the verdict

npm run cc -- loop status
OutcomeMeansDo next
passed green, spec intact, tests grewOpus referees the diff
the locked spec was edited it tried to buy a greenread the diff before re-running
tests were removed sameread the diff before re-running
budget exhausted 4 turns, still redthe spec is too big or too vague — split it

A failure is information, not a waste. Budget exhausted almost always means the Architect wrote a spec covering three changes instead of one. Splitting it and re-running usually costs less than one extra Opus turn.

8. What it will not do, on purpose

The grind stops at a green verifier. It does not commit, push, open a PR, or touch Jira — those are the steps where a mistake is expensive and hard to reverse, and they are exactly where a human reading the diff once is worth the minute it takes.

Two things that review must always cover, both learned the hard way here:

  • Audit moved code for drift. Extracted expressions must be verbatim. A subtly rewritten condition passes every test that did not think to check it.
  • Regenerate tracked build output. Where lib/ is committed, a PR whose source and build disagree is broken on arrival.

9. Before your first loop

QuestionIf the answer is no
Can you name one command whose exit code means "done"? You have a wish, not a loop. Write the spec first.
Have you watched it fail? A spec never red proves nothing. loop start will refuse it.
Is the target a worktree under this repo's tmp/? The driver refuses to start. The worker's tools are scoped to the window's workspace, so anything outside it stalls on a permission prompt.
Would you hand this repo to an agent anyway? Do not loop on it. The sandbox is not a security boundary.

Start it from a window open on this repo, and then leave that window alone

The driver opens no window. code chat -r dispatches into the last active one, and each dispatch starts a fresh chat session, so the worker never inherits the previous attempt's context. Two consequences. loop-worker resolves only from this workspace — chat.promptFilesLocations is workspace-relative and there is no user-level loop agent — so a window rooted elsewhere silently runs the default agent. And if you click into another VS Code window mid-run, the next dispatch follows you there.

10. Known limits

LimitDetail
Needs an open window Every successful dispatch fired with VS Code already running. Cold start is unverified.
One window, and it must be this one The driver opens nothing; -r targets the last active window. So the loop is started from a window on this repo, with the target as a worktree under tmp/. Click elsewhere mid-run and the next dispatch follows you.
One loop at a time Two concurrent loops would dispatch into the same window and interleave their turns.
Polling costs a full suite run 72 polls × 5s is up to 72 test runs per iteration. Fine at 90s; rethink at 10 minutes.
The copilot CLI is not an option Installed, but org policy denies every -p invocation. code chat is a different binary and is not blocked.
Chat hooks are unavailable The org flag forces them off, which is why the driver is bash outside the session rather than a hook inside it.
