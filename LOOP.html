Loop engineering

How a ticket becomes merged code without you driving each turn — and why the expensive model is deliberately kept out of the part that repeats.

This page assumes you have never run a loop. It explains the idea, the one property that makes it trustworthy, and the exact commands. The reference material lives in LOOP.md; this is the explanation.

1. The problem it solves

Ask an agent to do something and it will tell you it is done. Sometimes it is. The difficulty is that "I have completed the task" costs the model nothing to say and reads identically whether it is true or not. So you check. Then you ask for a fix. Then you check again. You are the loop, and you are the slowest part of it.

The fix is not a better prompt. It is to stop asking. Replace the question "are you done?" with a command whose exit code answers it, and put that command somewhere the agent cannot reach.

The one load-bearing idea

The agent never says whether it succeeded. It is not asked. A script outside the session runs the repository's own test suite and reads $?. That single change is the entire difference between a loop and a prompt you sent hopefully.

0. How to use it

Six steps, from a new chat

  1. Open a new chat session with + in the Chat view.
  2. Pick an agent from the table below. The wrong agent stops and names the right one.
  3. Pick the recommended model after the agent. Any model is allowed; an overpriced selection earns a warning, not a refusal. Agent re-selection reapplies its default. npm run --silent cc -- models self --session-log=<VSCODE_TARGET_SESSION_LOG> --tier=<tier> compares the selected model with npm run --silent cc -- models pick <tier>; it cannot prove which backend served the request.
  4. Write the goal and the repo (path or name under ~/dev/).
  5. Today: for an outside repo, add it to the workspace to edit, approve a per-call unsandboxed terminal prompt if shown, or scratch-clone a review target under bot/tmp/. Read-only list_dir may not prompt. No universal folder grant exists.
  6. Hands off while the loop runs. Expect LOOP RUNNING — hands off. and LOOP FINISHED with a ledger verdict, or an analyst's incremental tmp/<KEY>-report.md. The dashboard shows loop progress; do not touch the worker window, its files or driver. A blocked operation names the one action needed.

Target flow — designed, not built

The human picks the entry agent in the main window. It only enqueues, monitors and reports; durable supervisor/ tick code (no LLM and no approvals) dispatches architect, analyst, worker and tool-using judge into child windows by default, one per repo or item, with separate portable and user-data directories. A main-thread subagent may instead be dispatched for an appropriately scoped task — tool use included, not read-only or in-workspace only — subject to the same explicit, per-request approval and normal off-limits rules as any other main-thread action. A 2026-09-29 narrow proof showed one such approval granted by a pre-armed watcher without a person watching, for a call that read a file outside this workspace; whether confirmations generally block the parent, and general-purpose unattended approval, remain ASSUMED/UNKNOWN pending a broader S16 run. Durable, unattended loop work still favors the child by default for that reason — web fetches, repo work, git/gh, builds/tests, installs, writes and outside-folder reads default there, which opens on the repo or a scratch clone under bot/tmp/.

Designed approval: child profile self-approves permitted calls via approve-all, never by a UI click or forged consent. VERIFIED C-quinque 2 recorded TARGET True and run_in_terminal isConfirmed {'type': 1} after an unattended child touch; global approve-all and off-limits containment are UNKNOWN pending S13/S14/S18. System-file writes, secret reads/printing, the compiled denylist and gh pr merge stay off-limits. The last two are existing invariants flagged for a user decision, not silently dropped.

An off-limits pending call kills the child and parks the item with evidence. Another unexpected pending call gets one fresh-session retry, then parks. The code driver never waits for an answer: it moves on and produces one final parked-items report. It checks disk and ledger before retrying model errors, tries a same-tier single-model substitute, then tier escalation; exhausted work parks. This recovery is not built.

Today, avoid approval stalls

Prefer approval-free main-thread paths. Do not leave a main-thread subagent that may prompt when you walk away. Today's manual loop still needs an already-open repo window and real prompts must be answered by a person.

Resume after a closed window

Start a new chat with the same entry agent. Type resume <KEY>; repo <path>. Architect inspects tmp/<KEY>*, npm run cc -- loop status, the branch and PR (if remote). A saved driver can supply REPO=. Consult without judgment goes to the judge; committed spec without driver to arm; passed without PR to referee; open PR to feedback. A stale unclosed ledger row is not a pass. Analyst reads its report, then checks actual files. Artifacts outrank notes.

Supervisor & Mandatory Teardown (`npm run supervise`)

The loop supervisor orchestrates items across repos and guarantees zero leftover debris. Every child VS Code instance, watcher PID, portable/user-data profile directory, temporary spec, probe, or scratch directory is tracked in an owned-resource ledger (supervisor_resources) at creation and verified removed at item completion, cancellation, or supervisor shutdown. Deliverables, committed branches, and durable audit rows are preserved; temporary artifacts are cleanly purged.

# Add an item to the supervisor queue
npm run supervise -- add WS-6673 --repo=web-storefront-ui --brief="Cart drawer total fix"

# Reconcile desired state and run mandatory teardown on completed/cancelled items
npm run supervise -- tick

# Inspect status of queued, active, and torn-down items
npm run supervise -- status

# Cleanly cancel and teardown all temporary resources for an item
npm run supervise -- cancel WS-6673

2. The roles: a model never decides pass

The word "judge" hides an important split. Something has to decide what you want — that takes real intelligence. Something has to decide whether you got it — and that must not be a model at all, because a model can be argued into a yes.

RoleWhoRunsDecides
AnalystGemini 3.8 Flash or GPT-6 Sol by taskoutside the grindresearch, plan, investigation or draft review
Architect GPT-6 Sol once, up front; today in your chat, target in a child what "done" means — writes it as a failing test
Worker GPT-5.6 Luna once per iteration how to make that test pass
Gate no model every 5 seconds whether it passed — exit code and checksums
JudgeClaude Opus 5.5consult/referee; child by default for durable/tool work in target, main subagent permitted per-request for an appropriately scoped taskintent match, not test pass
Referee Architect + Judge once, at the end; child in target whether the pass is the one you wanted

Why this is cheap

The Gate sits between the Worker and the Referee, and the oracle judge never sees a red run. It is not in the polling loop, it does not read failure output, and it is not woken up between iterations. The architect prepares the red spec; the judge consults and referees only when needed, not on every poll.

Architect / Judgeintake and referee, plus consultsno

Model defaults come from registry/model-tiers.json and are stamped into agent frontmatter by npm run cc -- models apply. The driver dispatches with code chat -m loop-worker; change the registry, not a generated model line.

Target only: a child error triggers artifact inspection, one bounded rate-limit retry, same-tier single-model substitution, then tier escalation. An available-but-erroring first model does not fall through; code chat has no model flag (Spike 0 viii, LOOP.md §6a). Exact error field and single-model pin fidelity are UNKNOWN until S15. Exhaustion parks the item; other work continues.

Figure 3.1: The end-to-end loop cycle. Strong intelligence defines the red spec once up front; headless cheap workers iterate inside an unforgeable arithmetic gate; oracle intelligence audits the final delta.
#PhaseWhat happensYou do
0Intake Reads ticket or description, drafts assertions and consults the Judge on ambiguities only answer genuinely critical decisions
1Architect Writes those assertions as a real test, runs it, confirms it is red, commits it nothing
2Arm Copies scripts/loop.sh to tmp/ and fills it in nothing
3Grind Dispatch worker → poll → verdict → repeat, until terminal or out of budget run one command, then watch
4Referee Architect and Judge read the diff and accept, re-arm, or abandon spot-check if desired
5Close Commit and PR where remote; handle phase-6 review until merged, then resolve any ticket approve the PR if needed

You write requirements. It writes the spec.

This is the part that sounds harder than it is. Nowhere in the cycle are you asked to write a test. You give it the ticket — ordinary prose, the same words you would type into Jira — and phase 1 does the translation:

What you writeWhat it writes
“flag real differences, ignore noise” a test feeding it fixture page pairs and checking the verdict it emits
“it should be fast” a number — the suite must finish in under five minutes
“don’t hardcode selectors” a test that fails if any data-testid is declared outside pom.ts

That translation is why phase 0–1 uses the architect tier. Ambiguities and the referee verdict go to loop-judge; only genuinely critical judgments reach you.

5. Cheating, and the four ways it is caught

Exit code 0 is necessary but not sufficient. There are four cheap ways to make a test suite pass without doing the work, and a worker under time pressure will find them. Each gets its own terminal state, and every one is a fail — not a warning.

StateThe cheatHow it is caught
tamperededit the test until it matches the code sha-256 over the spec, re-read on every poll
shrunkdelete the failing tests total count must exceed the baseline
suppressedeslint-disable instead of a fix occurrences counted before and after
cfg-tamperedraise the guard limit you are failing sha-256 over the config file

Two design details worth keeping. Integrity is checked before the exit code, so a run that edited the spec is tampered even if the suite is green and the test count went up. And the checks are cheap enough to re-run continuously, so an invalid run is caught in seconds instead of after it has spent its whole budget.

6. Most tickets are not loopable

This is the part that saves you the most time, and it is the part everyone skips. A ticket qualifies as a loop only if all four of these hold. Check them before you write a spec, not after you have burned a budget finding out.

TestIt fails when…Example that fails
The verifier is local "done" is decided by a remote system "prove the Jenkins stage ran" — the answer is on a build server, not in $?
The verifier is red today the named gate already passes yarn lint && yarn test is green on main, so it can never signal completion
The deliverable is machine-checkable the output is prose a design document — no exit code can judge an argument
The inputs exist the agent would have to invent data a merchant cohort list nobody has supplied yet — it will make one up

The most common mistake, by a distance

Naming the repository's existing suite as the gate. yarn test passing does not mean your ticket is done — it means your ticket is not represented in it. A loop needs a new assertion that fails right now.

cc loop start refuses to open a run whose verifier already exits 0. When you see that refusal, the design is working. Go write the failing test.

The subtle case: when the deliverable is tests

If the ticket is "write a Playwright smoke suite", the worker is writing the very thing a spec would normally be — so there is nothing to lock. Lock a meta-spec instead: a test asserting the suite exists, covers the four merchant types, finishes inside its time budget, and hardcodes no selectors. That is the file the worker may not touch.

A ticket that fails this triage is not a worse ticket. It is work for a normal chat session with a human reading the output — which is most work, and that is fine.

7. Reading the verdict

npm run cc -- loop status
OutcomeMeansDo next
passed green, spec intact, tests grewOpus referees the diff
the locked spec was edited it tried to buy a greenread the diff before re-running
tests were removed sameread the diff before re-running
budget exhausted 4 turns, still redthe spec is too big or too vague — split it

A failure is information, not a waste. Budget exhausted almost always means the Architect wrote a spec covering three changes instead of one. Splitting it and re-running usually costs less than one extra Opus turn.

8. What it will not do, on purpose

The grind stops at a green verifier. It does not commit, push, open a PR, or touch Jira — those are the steps where a mistake is expensive and hard to reverse, and they are exactly where a human reading the diff once is worth the minute it takes.

Two things that review must always cover, both learned the hard way here:

  • Audit moved code for drift. Extracted expressions must be verbatim. A subtly rewritten condition passes every test that did not think to check it.
  • Regenerate tracked build output. Where lib/ is committed, a PR whose source and build disagree is broken on arrival.

9. Before your first loop

QuestionIf the answer is no
Can you name one command whose exit code means "done"? You have a wish, not a loop. Write the spec first.
Have you watched it fail? A spec never red proves nothing. loop start will refuse it.
Is VS Code open on the target repo? The dispatch will not fire. Every verified run had a window open.
Would you hand this repo to an agent anyway? Do not loop on it. The sandbox is not a security boundary.

One thing to check once, by hand

On your first run, confirm the worker really came up on the cheap model — open the chat window the driver dispatched into and look at the model picker. If a custom agent name does not resolve, code chat falls back to the default agent on whatever the window last used, and the loop still works. It just quietly costs what this design exists to avoid.

10. Known limits

LimitDetail
Needs an open window Every successful dispatch fired with VS Code already running. Cold start is unverified.
Only selected model is observable code chat has no model override flag; -m names an agent. Frontmatter defaults are stamped from the registry. models self reads the request-selected model, not independent backend-serving or billing evidence. Check the picker and session record on your first run.
One repo at a time The driver opens a window on the target. Two concurrent loops interleave windows.
Polling costs a full suite run 72 polls × 5s is up to 72 test runs per iteration. Fine at 90s; rethink at 10 minutes.
The copilot CLI is not an option Installed, but org policy denies every -p invocation. code chat is a different binary and is not blocked.
Chat hooks are unavailable The org flag forces them off, which is why the driver is bash outside the session rather than a hook inside it.

The obvious fix that is wrong: make the worker a subagent

Nearly every limit above comes from code chat. Dispatching the worker as a subagent would delete all of them at once — no window, no one-repo-at-a-time rule, and the model pin works there too.

But a subagent hands its result back to the turn that called it, so something expensive is awake for every iteration, reading every red run. Four iterations would cost four expensive turns — the exact cost §2 exists to delete. Two smaller losses follow: the checksum lock works because the driver is a file that can be hashed, and a chat turn is not; and a subagent chain only lives inside an open session, so there is nothing to start in a background terminal and walk away from. Target additional risk (ASSUMED, S16): a subagent confirmation may block the main window, so durable/unattended grinding still moves to child windows by default; a per-request, appropriately scoped main-thread subagent — tool use included — is permitted under the same explicit approval and off-limits rules as any other main-thread action. If you were going to watch the run anyway, the cost trade flips — but then it was never really a loop.
